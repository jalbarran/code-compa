# Spec 02: Mobile Companion Application (Expo)

This specification defines the behavior, user interface guidelines, state management, local connection handshake, and protocol integration for the Code Compa Mobile Companion application (`apps/mobile-expo`).

---

## 1. Overview & Goal

The **Mobile Companion** is a React Native app built with Expo that allows developers to remotely supervise, audit, and interact with AI agents running in their IDE on a development machine.

### Key Objectives:
- Scan connection QR codes from the IDE to initiate secure LAN pairing.
- Connect to the Go Bridge server over local Wi-Fi utilizing Connect-RPC.
- Maintain a real-time event stream (`StreamAgentEvents`) for agent telemetry and human-in-the-loop (HITL) requests.
- Provide a pixel-perfect, cohesive user interface for reviewing agent actions (such as terminal commands) and deciding options (approval, rejection, or feedback input).

---

## 2. Tech Stack & Engineering Constraints

To maintain lightweight development and clean visual design across multiple platforms, the mobile app strictly adheres to the following constraints:

### 2.1. Expo Go (Standard Environment)
- The app must compile and run in a standard **Expo Go** client environment.
- **No custom native builds:** Do not introduce third-party libraries requiring custom native modules, native build folders (`android/` or `ios/`), or Expo Development Builds, unless explicitly approved.
- All dependencies must be compatible with standard managed Expo SDK workflows (e.g., `expo-camera`, `expo-router`, `@connectrpc/connect`).

### 2.2. Tamagui UI Framework
[Tamagui](https://tamagui.dev) is the exclusive UI and styling system.
- **Cross-Platform Consistency:** Android and iOS screens and components must be visually identical.
- **No Platform Forks:** Never use `Platform.OS === 'android'` or `Platform.OS === 'ios'` checks inside component files to fork UI layouts. Visual adjustments must be achieved purely through dynamic responsive values or consistent custom styled-primitives.
- **Design Tokens:** Do not hardcode style properties (colors, spacing, font sizes, line heights, border radii). All UI definitions must consume tokens defined in `tamagui.config.ts` (e.g., `$color`, `$space.2`, `$radius.md`).
- **Primitives:** Construct all views utilizing Tamagui base primitives: `Stack`, `XStack`, `YStack`, `Text`, `Button`, `Input`, `Sheet`, etc.

### 2.3. React Native State Management (Zustand)
- Use **Zustand** as the lightweight state management store.
- **Store Responsibilities:**
  - Active connection credentials (IP, Port, Bearer Token).
  - Connection status (Disconnected, Connecting, Connected, Reconnecting, Error).
  - Queued intervention events received from the server stream.
  - History of resolved actions.

### 2.4. Local Networking & Security Exceptions
- Since local LAN hosts typically use unencrypted HTTP rather than certified HTTPS, cleartext traffic exceptions must be explicitly configured.
- **Configuration (`app.json`):**
  - **iOS:** Set `NSAppTransportSecurity` with `NSAllowsLocalNetworking: true` to exempt LAN IPs.
  - **Android:** Set `android.usesCleartextTraffic: true` in the Expo app config.

### 2.5. Connect-RPC Server-Streaming Polyfill (Expo Go Compatibility)
- **Constraint:** React Native's default JavaScript engine (`hermes`) does not natively include standard `TextEncoder`/`TextDecoder` and `ReadableStream` APIs.
- **Decision (Alternative B - Native Fetch with Polyfills):** In newer Expo SDK versions (SDK 56+ / React Native 0.85+), the native `fetch` implementation handles response streaming natively. To enable Connect-RPC stream decoding in this environment, we only need to polyfill text encoding and web streams:
  - Integrate the `web-streams-polyfill` and `fast-text-encoding` packages.
  - Initialize the polyfill libraries at the top of the entry point layout file (`apps/mobile-expo/src/app/_layout.tsx`) before executing any Connect-RPC client transactions:
    ```typescript
    import 'web-streams-polyfill';
    import 'fast-text-encoding';
    ```

## 3. Pairing & Connection Handshake (QR Flow)

Pairing is initiated by scanning the connection QR code generated by the IDE.

```
┌─────────────────┐           QR Code Scan           ┌─────────────────────┐
│   IDE Plugin    │ ───────────────────────────────► │ Mobile App (Camera) │
│ (Shows QR Code) │                                  └──────────┬──────────┘
└─────────────────┘                                             │
                                                                │ Extracts IP, Port, Token
                                                                ▼
┌──────────────────┐      Authorization Header       ┌─────────────────────┐
│    Go Bridge     │ ◄────────────────────────────── │ Connect-RPC Client  │
│ (Local LAN Port) │                                 │ (StreamAgentEvents) │
└──────────────────┘                                 └─────────────────────┘
```

### 3.1. QR Payload Format
The QR code displays a JSON object with connection metadata:
```json
{
  "ip": "192.168.1.15",
  "port": 8765,
  "token": "a1b2c3d4-e5f6-7a8b-9c0d-ef1234567890"
}
```

### 3.2. Handshake Steps
1. **Camera Permission:** The app checks camera access permissions using `expo-camera`. If denied, it presents a settings prompt.
2. **Scanner Screen:** A barcode scanner overlay captures the QR payload.
3. **Parsing & Validation:**
   - On successful scan, the app parses the JSON payload.
   - If invalid, it raises a temporary error alert and resets the camera capture.
4. **Credential Storage:** Store the extracted `ip`, `port`, and `token` in the Zustand store.
5. **Connection Attempt:** Configure the `@connectrpc/connect` transport layer pointing to `http://<ip>:<port>` and immediately transition to the Dashboard/Stream screen.

## 4. Connection & Event Streaming Lifecycle

Once paired, the Mobile Companion maintains a persistent connection to the sidecar.

### 4.1. Transport Protocol
- Configure `ConnectTransport` from `@connectrpc/connect-web`.
- Use a **headers interceptor** to inject the bearer token in every RPC call:
  ```http
  Authorization: Bearer <token>
  ```

### 4.2. Streaming Stream Lifecycle (`StreamAgentEvents`)
- Establish a stream connection calling `client.streamAgentEvents({})`.
- **State Flow:**
  - **Connecting:** Attempting to establish the connection stream.
  - **Connected:** The stream is active.
  - **Disconnected / Error:** If the stream drops or fails, perform a retry loop:
    - Automatically attempt reconnection up to 5 times.
    - Implement exponential backoff (e.g., 1s, 2s, 4s, 8s, 16s).
    - If all retries fail, return to the Scan screen with a visual error alert.

### 4.3. Event Queue & Store Logic
- Incoming `AgentEvent` payloads are appended to the queue in the Zustand store.
- **Deduplication:** Verify that incoming event IDs do not already exist in the queue before adding.
- **Ordering:** Maintain events in reverse chronological order (newest first).

## 5. UI Layout & Screen Flows

The app consists of two primary views: the **Scanner Screen** and the **Dashboard / Decision Screen**.

### 5.1. Scanner Screen (Initial State)
- Rendered when there is no active pairing configuration in the store.
- Displays a clean visual camera frame targeting the QR code.
- Features a mock connection button for local testing (allows manual entry of IP, Port, and Token in development).
- Uses Tamagui theme colors for clear error/success overlays.

### 5.2. Dashboard & HITL Decision Screen
- **Header:**
  - Shows current connection status (green indicator for Connected, yellow for Connecting/Reconnecting, red for Disconnected).
  - Displays the target host IP and a "Disconnect" button.
- **Empty State:**
  - Renders a visually pleasing confirmation if the event queue is empty (e.g., "Agent running autonomously. No intervention required.").
- **Intervention Card (Pending Action):**
  - Displays details of the most critical pending `AgentEvent` at the top of the queue:
    - **Header:** App name / IDE identifier (e.g., "VS Code - Antigravity_2.0"), agent name, and timestamp.
    - **Command Card:** Renders the command to execute formatted inside a syntax-highlighted code block, including the working directory.
    - **Risk Badge:** Color-coded indicator depending on `risk_level` (e.g., "High Risk" is vibrant orange/red, "Low Risk" is subtle blue/gray).
    - **Action Controls:**
      - If `options` are provided, maps them directly to Tamagui `Button` components (e.g., "Approve", "Deny").
      - If `allows_text_input` is true, displays an `Input` field for custom developer instructions/feedback.
    - **Submission:** On button press, locks UI interaction, dispatches `RespondToIntervention`, removes the event from the active queue upon success, and stores it in history.

## 6. Verification & Success Criteria

To verify compliance with the spec:

### 6.1. UI Visual Integrity Checks
- Verify using simulators/devices that all buttons, sheets, and fonts look identical on both iOS and Android.
- Ensure that the application adapts smoothly to both system Light and Dark themes via Tamagui configurations.

### 6.2. Protocol Validation (Mock Server Integration)
- Verify that standard HTTP POST/streaming requests include the `Authorization` header with the correct Bearer Token prefix.
- Validate that the app correctly parses QR JSON codes and transitions states appropriately.
- Simulate network drops (e.g., shutting down the mock server) and verify the exponential backoff reconnection flow.
